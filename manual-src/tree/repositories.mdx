A **repo node** brings a coding project into the same workspace as its plans, research, screenshots, and conversations with Joe. Browse files, edit several at once, compare changes, make commits, and explore branches without losing the project’s visual context.

Folders become child nodes and files become gallery items. Switch between the Canvas and File Explorer to see the project as a reference board or as a code workspace.

## A quick tour of the coding workspace

| What you want to do | Where to go |
| --- | --- |
| Work across several files | **File Explorer** and editor tabs; each file keeps its draft and undo history. |
| See what you changed | **Diff** compares your current file with its last commit. |
| Save a milestone | **Source Control → Changes**: stage files, write a message, and **Commit**. |
| Explore earlier work | **Timeline** for a file, or **Graph** for commits and branches. |
| Try a different direction | Create a branch and **Open Branch as Node** to give it a place in the tree. |
| Work with a teammate | Share the repository; permitted browser guests use its Explorer, editor, and Source Control through your computer. |

**Save** updates the working file. **Commit** records a chosen set of saved changes in Git history. **Push** sends commits to the linked remote repository.

<Note>
A repo node is the Git boundary for a project. A **Workspace Folder** chooses where the whole Flow is stored. They are separate features: do not make the whole Workspace Folder your project repository. See [Workspace Folders](/workspaces/folders).
</Note>

## Shared repositories

Guests use the same Explorer, editor and Source Control surfaces. **Can view** allows reading shared files and their associated history. **Can edit** allows creating, editing, renaming, saving and committing shared files through the owner's computer. Saving and committing are separate actions. Credentials and native filesystem paths stay with the owner, and a scoped commit preserves private and unshared files.

The Graph includes branches in the shared repository, including branches not yet open as Flow nodes. A branch represented by a private or unshared node stays unavailable. Guests can read admitted branch history, tags and stashes. Edit guests can create branches and tags, open a branch as a node where that keeps it inside the shared area, merge shared changes, and use Fetch, Pull and Push through the owner's computer. An Edit guest merges exactly as the owner does, FlowJoe's notes, layout and history included, and answers FlowJoe's questions about what they can see. Folders kept from them keep the owner's version and are never shown to them. An Edit guest can also change a repository's history choices, and reads and writes the history of the items and folders they can see. Their Changes list shows FlowJoe's notes, layout and history for what they can see, and their commits write them, as the owner's do. An Edit guest can run **Update Gallery** too and answer questions about conflicting changes they can see. It runs on the owner's computer, so folders kept from them are brought up to date without being shown to them.

Discarding working changes, saving a stash that puts files back to their last commit, applying or popping a stash over existing work, rewriting the last commit, renaming or deleting branches, deleting tags or stashes, and replacing or removing a remote require the owner's additional removal permission. Linking a new remote does not. Private and unshared file contents stay protected when changes are merged, pulled, committed or restored. A guest push stops if the branch or tag history contains private or unshared files, because Git would send that history to the remote. Fully shared repositories can be pushed normally. A partially completed stash operation reports that some files could not be changed; the saved stash remains available.

Removing your own created file requires no extra removal permission when it has no protected contributions from others. Removing someone else's file requires the owner's additional removal permission. Editing its text does not make you its creator. Private content remains unavailable with either permission. See [Sharing, Guests and Presenting](/workspaces/sharing-and-presenting).

## Create or open a repo node

Create, clone, and import repositories in the desktop app. A standalone browser session cannot run native Git; invited guests use the owner’s shared repository tools.

Use the **New Node** window to create an empty repository or clone from a Git remote. To import an existing local Git folder, drag the folder onto the Flow tree and choose **Import as Repository**. (The other choice, **Import as Ordinary Folder**, brings it in as a normal folder.) A repo node is the Git boundary for that project: folders become child nodes and files become gallery items. FlowJoe keeps the bare Git history in its own hidden storage and saves the working files through the Flow's normal storage. It does not create a checkout folder elsewhere on your computer, and it does not put the whole Flow into Git.

For a remote, use its HTTPS address or, on macOS and Linux, either SSH form shown by the Git host, such as `https://host/owner/project.git`, `ssh://git@host/owner/project.git`, or `git@host:owner/project.git`. FlowJoe uses one remote named `origin` for each repo node. A repository imported from a local Git folder can keep its existing SSH origin on macOS and Linux. On Windows, SSH addresses are not supported yet: use an `https://` address instead.

When you open a repo node, choose **Source Control** in the app rail. The repository appears with its current branch and any changes waiting to pull or push. The panel is available to the owner and to browser guests with repository access. View guests read shared files and history; Edit guests save and commit through the owner.

## Make a branch a repository

An Edit guest can make a shared branch a repository through the owner's computer. The owner's complete branch is converted, including folders hidden from the guest; those folders are never shown to the guest. Private folders stay home. Names that need fixing are fixed on the owner's computer.

Any branch of your tree can become a repository: right-click its top node and choose **Make This a Repository…** in the menu's **Organize** section (desktop app, owner only). Nothing changes until you confirm. A window shows first:

- **What goes in:** how many nodes, files and links. Every node becomes a folder, every item becomes a file (pictures and documents as they are, a link as a `.url` shortcut), and FlowJoe's small hidden files keep titles, notes, order, canvas layout, themes, tags and automations (switched off for anyone who clones).
- **What stays on this computer:** where you are scrolled and zoomed, and your app-wide fonts, text size, line spacing and density. A linked file (one that points at a file elsewhere on your computer) stays here too.
- **Private nodes:** each Private node starts unticked and stays out, with everything in it. To include one, tick it and enter its password. FlowJoe then warns you plainly: the lock only works inside FlowJoe, so anyone who opens the repository's files directly (on GitHub or in an editor) can read that node, because it is not encrypted, and Git keeps it in the history even if you delete it later or the repository becomes public. An included node keeps its lock: someone who clones the repository sees it locked in FlowJoe and opens it with the same password. Your password itself never goes into the repository. A Private node inside one you included stays out unless you tick it as well. When anything Private goes in, the repository's history stays on this computer, never in a shared Workspace Folder.
- **History:** the same choices as `.fj` export, all off to begin with: **Include AI chat and image history** (your Joe chats and the pictures Joe made), **Include picture prompts** (the prompt that made each AI picture), **Include Transcript History** (kept transcripts and their edits), **Include undo notes history** (the undo and redo steps of notes, titles and summaries) and **Include Memories** (what Joe remembers about these nodes and items, and the Flow's own Memories). See [History in the repository](#history-in-the-repository). The repository remembers these choices, and so does every copy someone clones.
- **Names to fix first:** in a repository a title is also its file or folder name, so two titles that would clash (capitals don't count) or a title with characters files can't have are listed with a suggested name. **Accept Fixes and Make Repository** renames them (each rename can be undone like any other) and then makes the repository. To pick your own names, cancel, rename them, and start again.
- **Where it goes:** **Keep it on this computer for now**, or **Link a GitHub repository** with its link (or `owner/name`). Linking only connects it; push from **Source Control** when you're ready.

**Make Repository** makes the first commit straight away, signed with your Git name like any other commit, and **Source Control** shows the new repository with nothing left to commit. **Undo** turns it back into an ordinary node.

A branch that already holds a repository can't become one (a repository can't hold another one). FlowJoe says which repository is inside it and offers **Show** to select it, so you can move it out first or choose a different branch.

## Browse and edit repository files

Joined guests use the same Explorer and Source Control through the owner's computer. View reads shared files and history; Edit saves and commits. Elevated removal is required for actions that discard work or rewrite history. Private files and branches stay excluded. The supported actions are described under **Shared repositories** above.

Choose **Switch to File Explorer** in the repository gallery to show its folder tree and editor. Select a file row to open it in the workbench. Resize the Explorer divider by dragging it or using the keyboard, and use the file tabs to move between files. Each file keeps its own draft and undo history while you switch tabs.

Choose **Switch to Canvas** to return to the repository’s normal gallery.

Paths are relative to the repository root (`.`), such as `src/main.js`; FlowJoe does not create a checkout folder on your computer. From a folder or the Explorer background, use **New File…**, **New Folder…**, or **Quick Open…**. New File and New Folder place a name field in the Explorer at the target directory. Press **Enter** to create it; **Escape** or leaving the field cancels. Name or save errors stay beside the field so you can correct the name. A folder menu can copy that folder’s relative path; the root/background menu has no path to copy. New files need a supported text extension.

The editor toolbar has **Save**, **Diff**, **Find**, **Format**, and word wrap; the active FlowJoe theme applies to the editor. Undo and redo are available through the editor’s standard commands. **Diff** compares **Last commit** on the left with the editable **Current file** on the right, including unsaved edits. **Save** writes the current file to repository working content and updates Source Control; it does not create a Git commit. To commit, go to **Source Control → Changes**, stage the files you want, enter a message, then choose **Commit**. A historical revision is read-only. **Restore This Version…** copies that revision into the current working file; it does not create a commit.

For JavaScript and TypeScript, nearby repository files can help the editor offer suggestions. The workbench does not run your project or provide every service of a standalone development environment.

Renaming a branch or changing its remote keeps open editor drafts available. Stash, Pop, Apply, and Close Branch Node ask you to save or discard unsaved editor work before changing files; Cancel keeps your work in place.

If you discard a folder deletion, FlowJoe restores its recorded folder protection and creator information along with the files, including after reopening the Flow on this computer. Restoration stops if that information is unavailable, a path now belongs to something else, or a protected folder is locked.

## Review and commit files

The **Changes** section lists files that differ from the last commit. Its menu offers **View as Folders** to group the list by folder and **Open Changed Files** to open every changed file. Stage the files you want to include, write a commit message, then choose **Commit**. **Generate** can draft a message from the changes. Generate and Joe reviews leave out Private and Hidden-from-Joe file contents, including protected folders; unlocking a Private folder for yourself does not share it with Joe. You can also review a changed file before committing, discard a change, or use the split button for commit-and-push or commit-and-sync actions.

### Private folders in a repository

A Private (password-protected) folder inside a repository stays on your computer. Its files appear in **Changes** under **Private · stays out of commits**: you can open them, but they are never staged or committed, and pushing never sends them. A file that was committed before its folder became Private stays at that committed version.

If commits made earlier already include files from a Private folder and haven't been pushed yet, **Push stopped** explains what was found and offers **Remove Them and Push**. FlowJoe rewrites only those unpushed commits without the Private files (tags on them move along), then pushes; your files stay on this computer. Merging a branch that changed a file in a folder you later made Private doesn't stop the push: the merge keeps your version. Nothing changes if FlowJoe can't reach the remote to check what it already has. **Push Tags** also stops if a tag points at an unpushed commit with Private files.

A branch opened as its own node follows the same Private folders. If the repository itself is Private, the whole repository is yours to commit and push as before; Source Control shows a key on it.

A Private folder you included when you made the repository (see **Make a branch a repository**) is committed and pushed like any other folder, with its lock. When someone clones it, it arrives locked (the same password opens it) and stays included, so their changes to it are committed and pulled like any other folder's, and a merge never puts an older version back. If you remove its password and later set a new one, it stays out of Git from then on: its later changes are held back like any Private folder's.

New files added through the repo node's gallery appear in **Changes** so you can stage them. Imported executable-permission changes also appear, even when the file text is unchanged.

### What goes into the repository

Besides your files, a commit can record what you arranged in FlowJoe, so teammates who clone the repository see the branch the way you made it. Each folder with something FlowJoe-specific to say gets one small hidden file (`.flowjoe-node.json`, plus `.flowjoe-repo.json` at the top). It holds:

- folder titles, node summaries, status, and slot and stack notes,
- the order of slots and folders, the gallery layout, a chosen canvas arrangement and where you placed slots on the canvas, slot colours and connections,
- tags on nodes and slots (each tag travels with its name, colour and description),
- placeholder slots, and which picture a stack shows,
- automations, which arrive switched off on the other computer.

Where you are looking on the canvas stays with you. Your Joe chats, picture history, transcripts, undo notes history, Memories and picture prompts stay with you too, unless the repository includes them (see below). A plain code repository gets no FlowJoe files until you add something like a note. A folder with no files is kept in Git through its FlowJoe file.

### History in the repository

A repository can carry the history around its items, the same history a `.fj` export can carry. Each kind is a separate choice, and each starts off:

| Choice | What goes in |
|---|---|
| **Include AI chat and image history** | Joe chats about each slot and node, and the pictures Joe made, with their pictures |
| **Include picture prompts** | the prompt that made each AI picture |
| **Include Transcript History** | kept transcripts and their edits |
| **Include undo notes history** | the undo and redo steps of notes, titles and summaries |
| **Include Memories** | Memories saved on a node or slot, and the Flow's own Memories |

You choose when you make a branch a repository. To change the choices later, open **Source Control**, choose **…** on the repository row, then **History in This Repository…**, and **Save** (an Edit guest can too). Turning a choice off stops adding new history. What is already committed stays in the repository's history, because Git keeps everything it has recorded.

What goes in, and what doesn't:

- **History travels with its item.** Each item's history is kept beside its folder, in a hidden `.flowjoe-history` folder that FlowJoe never shows as a folder or slot. When the item moves, its history moves with it. When the item is removed, its history is removed too.
- **Stays on this computer:** a conversation or transcript you marked to keep on this computer, and everything in a Private folder you didn't include. A Flow-wide Memory made from a chat in such a folder (or in a Private node elsewhere in the Flow) also stays here. A Private folder you included shares its history like everything else in it.
- **Someone who clones** gets the history on the same items, as their own copy. A Flow-wide Memory arrives as a Memory of the repository node, so it doesn't spread across their whole Flow. **Open Branch as Node** copies the history into the new node, as **Duplicate** does, and your Flow's own Memories are not copied twice.
- **Two people's history is always kept.** When you merge or update the gallery, both sides' messages, transcripts and Memories are kept, in date order, and the same message is never doubled. FlowJoe never asks a question about history. If the same Memory or transcript was edited in two ways, both versions are kept.
- **Deleting removes it.** Delete a chat, a message, a transcript or a Memory, and your next commit takes it out of the repository; teammates lose it too when they update their gallery. If a teammate changed that same entry in the meantime, their version is kept. Past commits still hold it, as they hold any deleted file.
- **Pictures stored with Git LFS.** If the repository sends pictures to Git LFS, a history picture that arrives as an LFS file is not downloaded with the history: the entry keeps naming it and nothing is lost.

**Update Gallery** brings a teammate's new history in, and takes out what they deleted, even when nothing else changed. Its **Undo** puts the gallery back, but history that arrived stays with you. **Undo** of a clone or of **Open Branch as Node** takes the history that came with it away again.

### Everything you add becomes a file

In a repository, everything in a gallery is committed as a file that opens outside FlowJoe too, and comes back as the same kind of slot when someone clones the repository:

| In FlowJoe | In the repository |
|---|---|
| A link | `Title.url`, an ordinary internet shortcut |
| A spreadsheet, rich document or calendar | `Title.fjsheet`, `Title.fjdoc` or `Title.fjcal`: FlowJoe's own file, the same data a `.fj` export carries |
| A calendar event | `Title.fjevent` |
| A picture you generated, pasted or copied in | the picture file itself (its prompt stays with you unless the repository includes picture prompts) |
| A placeholder | nothing extra: it lives in the folder's FlowJoe file |

When you edit a spreadsheet, document, calendar or link, its file changes too and shows in **Changes**. These files are written from their slots, so the file editor shows them read-only: change a link's address or a spreadsheet in its own slot. The first time you open **Changes** in a repository you cloned or made before this, its links and other items show up once as new files. Every node inside a repository node is a folder: a node you add, or move in from elsewhere in the tree, gets a folder named after its title. If a node made before this already holds files, they move into its own folder, so your next commit shows them as renamed. A folder you move in from another repository keeps its files as they are (executable scripts and symlinks included), and a folder you move out and back in comes back unchanged. Undoing such a move puts everything back as it was. If a moved-in file's picture or bytes aren't on this computer, it stays out of commits and **Changes** says so. **Discard Changes**, stashes and **Pop** bring a link, spreadsheet, document or calendar back as itself.

**Limits:** a linked file (one that points at a file elsewhere on your computer) stays on this computer and is not added; **Changes** says so in a line under the list. A Private node you move in stays out of every commit and push, as any Private folder does. A virtual slot is a pointer to its original, so only the original is a file. Automation slots aren't committed yet.

### Titles are file and folder names

In a repository a title is also its file or folder name, as in a code editor. Renaming a node in the tree renames its folder, and everything inside moves with it; renaming a file slot renames its file. If you leave off the extension, FlowJoe keeps it: retitling `photo.png` to "Hero" names the file `Hero.png`. Git records these as renames, and notes stay with the renamed files.

A folder that holds a locked Private folder can't be renamed or moved to another folder until you unlock it, because the Private folder's files have to move with it. A name that another file or folder beside it already has is refused, even with different capitals ("Notes" and "notes" are the same name on macOS and Windows), and so is a name with characters files can't have, such as `: / \ * ? " < > |`. FlowJoe tells you why and keeps the old name, the same way from the tree, a slot's title and the Explorer.

When you change only notes or layout, **Changes** shows one row per folder: the folder's name with **Notes and layout** (the repository's name for the top level). Stage and commit it like a file. These rows can't be opened or discarded yet. A Private folder's notes are committed only if you included that folder when you made the repository, and if the whole repository is Private, FlowJoe leaves its notes and layout out of commits for now.

When you clone a repository made in FlowJoe, its notes, order, layout, tags, placeholders and links appear in the new node. Tags you already have keep your own colour. If FlowJoe can't read those details (for example, they were saved by a newer FlowJoe), the files still arrive and a notice says what couldn't be used; FlowJoe never overwrites details it can't read.

When a merge leaves conflicts, the Changes menu offers **Mark All Resolved**, which becomes available once you have resolved every conflict yourself; FlowJoe never picks a side for you.

### Merging FlowJoe's notes and layout

When you merge a branch, FlowJoe's own files are merged as FlowJoe things, never as text: slot by slot and field by field, against the point where the two branches split. Notes on one slot and tags on another, or a teammate's notes on a different slot, simply combine. Tags added on both sides are all kept. When both branches reordered a gallery and the moves fit together, both are kept. What both branches changed in different ways (the same slot's notes, a folder's status, two orders that contradict, a slot removed on one branch and edited on the other) becomes a question in the same window as above, with **Yours, on main** and **From feature** side by side and **Finish Merge** at the end. Closing the window leaves the merge waiting under **Merge Changes**, where the folder's **Notes and layout** row opens the questions again. Plain files that Git can't merge still open the file editor afterwards; if a choice there raises a new question (for example you keep deleted the only file of a folder whose notes you changed), FlowJoe asks it before the merge is committed. Before the merge commit is made, FlowJoe checks that the merged notes and layout read back correctly. A Private folder's notes are never read or merged, and if the other branch renamed it, it stays where it is here instead of arriving a second time under the new name. If the other branch renamed or moved that folder, FlowJoe still recognises it when it keeps FlowJoe's own id for it or still holds most of the same files; a folder that was renamed and also had most of its files changed can't be recognised. Automations merged in stay switched off. An Edit guest merges these the same way, answering only questions about what they can see.

Right-click a file, folder, or tab for actions that fit what you selected:

| Where | Useful actions |
| --- | --- |
| **File** | Open, preview, compare, Timeline, rename, cut, copy, move, download, delete, and copy its name or relative path. |
| **Folder** | New File, New Folder, Quick Open, Find in Folder, rename, cut, copy, paste, move, delete, and copy its name or relative path. |
| **Tab** | Close this tab, other tabs, tabs to the right, saved tabs, or all tabs; reveal the file in Explorer, preview it, open Timeline, or rename a working file. |

To rename a file, folder, or working-file tab, double-click its name, press **F2**, or choose **Rename…**. Press **Enter** or leave the field to save; **Escape** cancels. Errors stay beside the name so you can correct them. Older revisions are read-only, and the repository root cannot be renamed, moved, or deleted through Explorer.

Renaming a folder updates the paths of all files and subfolders inside it. Renaming or moving a working file keeps its open draft and undo history. **Delete…** on a folder confirms the folder and its contents; any affected unsaved files must be saved or discarded before deletion can finish. Canceling or a failed save keeps the folder. File deletion also checks for new edits when its turn arrives; the file cannot be edited while deletion is being saved.

**Cut** followed by **Paste** moves a file or folder within the same repository. **Copy** followed by **Paste** creates independent items. Pasting a copy into its original folder chooses a free name such as `README copy.md`; an existing destination elsewhere is never overwritten. **Move to Folder…** offers a destination picker. A folder cannot be moved into itself or one of its descendants. If a copy includes drafts, choose **Save and Copy**, **Copy Saved Contents**, or **Cancel**; copying saved contents leaves the source drafts untouched.

A folder’s **Quick Open…** lists only files inside that folder and its descendants. **Find in Folder…** searches readable text there, including unsaved open drafts; selecting a result opens the file at the matching line. Binary files are skipped. Large searches show a limit notice so you can narrow the query. Closing the search, switching repositories, or locking protected content clears the results.

Choose a tab close action to close the selected file or group. If any affected file has unsaved edits, FlowJoe asks whether to save, discard, or cancel; a canceled close or failed save leaves the file open.

### Explore history and ask Joe

A file’s **Timeline** follows its branch, including after a rename or move. Open an earlier version, compare it with today’s file, or choose **Restore This Version…** to bring its contents back into the working file. Restoring does not create a commit. A deleted folder is restored only when its original identity and current branch baseline can still be verified; a new folder with the same name does not take its place. If a restore’s save cannot be confirmed, the restored file and its bytes stay available for recovery; the operation does not claim that it was saved.

**Open Changes** opens a separate comparison tab labeled with the file and revision. Older comparisons are read-only on both sides; your working tab and unsaved draft stay available. Reopening the same comparison selects its existing tab. Renaming the branch or changing its remote keeps both pinned sides available.

In **Changes**, choose **Review Changes with Joe…** for the current edits. Timeline offers **Review Change with Joe…**, and the commit Graph offers **Review Commit with Joe…**.

The Graph also lets you compare a commit with its parent, your current branch, or another selected commit; create a branch or tag at that point; open it on GitHub; or copy its commit message or identifier. Unavailable actions are dimmed.

## Keyboard controls

With focus in the workbench, **Ctrl/Cmd+S** saves and **Ctrl/Cmd+F** finds text in the file. Focus a file row, folder row, or working-file tab and press **F2** to rename it inline; press **Enter** to accept or **Escape** to cancel. **Shift+F10** (or the Context Menu key) opens the menu for a focused Explorer row, tab, or Timeline entry.

Use the divider’s arrow keys to resize the Explorer; hold **Shift** to move it farther, and use **Home** or **End** to move to a limit. **Quick Open…** is available from the Explorer folder/background menu. With focus on an Explorer row, **Ctrl/Cmd+X**, **Ctrl/Cmd+C**, and **Ctrl/Cmd+V** cut, copy, and paste repository items. These shortcuts keep their normal text-editing behavior inside name and search fields.

## Work with branches

The branch pill opens the repository's branch list. You can create a branch, rename or delete one, or merge it into another branch. **Delete Branch** asks you to confirm and warns you when the branch holds commits that exist only on this computer, when they are not on GitHub, or when FlowJoe could not check. A branch that a node is open on cannot be deleted until you close that node.

Choose **Open Branch as Node** to put a branch in the Flow tree as its own node. Each open branch node shares the repository's history. A folder that is Private in the repository opens locked in the branch node too, with the same password; removing the password from one copy doesn't change the other. If the whole repository is Private, its branch node is Private as well. To work on another branch, select its node in the tree; **Switch Branch** opens that same branch picker. To remove a branch node from the tree without touching the branch, choose **Close Branch Node…** and confirm; the branch and its commits stay in the repository. You get 5 seconds to **Undo**, which brings the node back with its automations and keeps its media safe.

## Sync with a Git remote

Use **Fetch** to check the remote for new commits. The repository row and Graph toolbar also provide **Pull**, **Push**, and sync actions. The row's counts show changes waiting to come in or go out. Link, change, or remove the remote from the repo node's **…** menu under **Remote**.

### Bring a teammate's changes into your gallery

Pulling (or merging another branch) downloads the new commits, but your gallery is not changed on its own. A row appears under the repository saying who sent changes, for example **3 changes** from Sam, with a **Review** button.

**Review** opens a window that lists, in FlowJoe terms, what will change:

- **Added**: new slots and folders.
- **Changed**: pictures or files replaced, notes edited, slots moved on the canvas, a folder's layout or order.
- **Renamed**: files and folders with a new name. Their notes, chats and Memories stay with them.

If the repository includes history, a teammate's new chats, transcripts and Memories come in at the same time (see [History in the repository](#history-in-the-repository)).
- **Removed**: slots and folders your teammate removed.
- **Needs your choice**: things you both changed in different ways, and files you have open in the editor with unsaved changes.

Choose **Update Gallery** to bring everything in at once, or **Cancel** to leave the gallery as it is. If something needs your choice, FlowJoe then asks about it, one question at a time (see [Answer FlowJoe's questions](#answer-flowjoes-questions)); **Finish Update** applies the update with your answers. Your own changes that aren't committed yet are kept. Before the update, FlowJoe saves a restore point in Version History named *Before updating "…" from Git*, and **Undo** takes the whole update back in one step.

Private and frozen folders are left exactly as they are, even if your teammate renamed or removed the folder they are in. The window only says how many of their changes were left out, without naming them. If you change the gallery while the update is downloading, FlowJoe stops and asks you to review again rather than overwrite your work.

Once every question is answered, the row leaves and the gallery is up to date. If you cancel the questions, nothing changes and the row stays, so you can review again later.

### Answer FlowJoe's questions

When you and someone else changed the same thing in different ways, FlowJoe asks in its own terms, never as text with conflict markers. Each question names the slot or folder (for example *You and Sam both changed “brief.pdf”*) and what changed (**Slot notes**, **Name**, **Order of slots**, **Tags**, a canvas place…), shows your version and theirs side by side, and offers:

- **Keep Mine**: your version stays.
- **Keep Theirs** (or **Keep Sam's** when FlowJoe knows who sent it): their version replaces yours.
- **Keep Both**, for notes and other text: their text goes under yours, so you can edit them together.

A slot one of you removed while the other changed it is kept until you answer: **Keep Mine** or **Keep Theirs** decides whether it stays. For a file you have open with unsaved typing, **Keep Theirs** puts their version in place (or removes the file, if they removed it), throws your unsaved typing away and closes its tab; your own notes and tags on that slot stay. **Keep Mine** keeps the typing. **Previous** and **Next** go back to a question you already answered, to change it. Where taking theirs isn't possible (it would move a Private or frozen folder, or a name is already used here), only **Keep Mine** is offered. **Cancel**, the ✕ or Esc close the window without changing anything.

### Sign in to GitHub over HTTPS

For private GitHub repositories over HTTPS, choose **Sign in with GitHub** in Source Control. FlowJoe opens Git Credential Manager's sign-in flow. This signs in HTTPS GitHub access; SSH remotes use your SSH agent instead. Your GitHub account also lives in the Source Control **…** menu, which shows **Signed in as …** and offers **Sign Out of GitHub**.

Cloning a private repository from the **New Node** window works the same way. If GitHub says the repository is private or can't be found, the window says so and offers **Sign in with GitHub** right there; once you're signed in, the clone runs again by itself. If you're already signed in and that account has no access, the window names the account and offers **Try Again** (after the owner adds you as a collaborator) or **Use a different GitHub account**. FlowJoe never opens a sign-in by itself.

### Large files (Git LFS)

Many repositories keep big pictures, videos and other media in **Git LFS** (Large File Storage): the repository itself holds only a small placeholder, and the real file lives on the hosting service. FlowJoe reads these by itself; you never install anything.

When you clone, pull, or choose **Update Gallery**, each large file arrives as a slot that says **Not downloaded yet**, with the file's name and its real size. FlowJoe never shows the placeholder's text as the file. To get the file, open the slot (click it), choose its **Download** button, or open it from the **Explorer**. FlowJoe checks that what arrives is exactly the file the repository names before it keeps anything; if it isn't, nothing is saved and FlowJoe says so. Offline, or if anything goes wrong, the slot stays **Not downloaded yet** with a plain message, and nothing is lost: try again later.

While a file downloads, a small **✕** sits next to **Downloading…**. Choose it (or press **Escape** while it has focus) to stop the download: nothing is kept, and the slot goes straight back to **Not downloaded yet**.

A downloaded large file never shows up in **Changes**: it's the same file the repository already has. A file in a Private folder is saved as Private, like the rest of that folder, and a locked Private folder must be unlocked first. A repository you cloned before FlowJoe could read large files shows their placeholder text at first; the next time you open **Changes**, those slots become **Not downloaded yet** by themselves, and nothing shows up as changed.

**Sending large files.** Any file of **50 MB or more** goes through Git LFS, and so does any file at a path the repository's `.gitattributes` already marks for Git LFS. FlowJoe keeps the file's bytes in the repository's own large-file storage on your computer and commits only the small placeholder, so someone who clones with plain Git and Git LFS gets the real file. The first time you commit such a file at a new path, FlowJoe also adds one line for it to the repository's `.gitattributes` file, which appears in the gallery like any other file. In **Changes**, a large file shows like any other file with a small **Large file** note. A file you downloaded and haven't changed stays exactly as it was: it is never committed or sent again.

When you **Push**, FlowJoe first sends the large files the new commits carry, then the commits. If the large files can't be sent (no connection, no access, or the server's large-file storage is full), nothing is pushed, your work stays as it is on this computer, and FlowJoe says why in plain words. Files in a Private folder are never sent, and FlowJoe checks the Private rule before anything goes up.

**The first push.** Before a repository's first push, FlowJoe shows how much will go up: the total size, the number of files, and what goes through Git and what through Git LFS. Choose **Push** to send it, or **Cancel** to send nothing. On GitHub, large files count against your GitHub storage.

**Limits.** Large files have no size limit in FlowJoe; the hosting service sets its own. Ordinary files, under 50 MB, stay in Git as they always have; FlowJoe still refuses a single ordinary Git file over 100 MB when you clone or import a repository that already holds one.

- **Signing in.** Large files on GitHub use the same GitHub sign-in as cloning a private repository (above). FlowJoe sends your sign-in only to the repository's own host when it asks where the file is, never to the server the file then comes from.
- **SSH links.** A repository you cloned with an SSH link (`git@github.com:…`) downloads its large files from the same host over HTTPS. On GitHub that uses your GitHub sign-in: if you aren't signed in, or your account can't see the repository, FlowJoe asks you to sign in with GitHub. On another host with no HTTPS download for them, FlowJoe tells you that large files need an HTTPS link.
- **A different large-file server.** If a repository names its own large-file address (in a file called `.lfsconfig`), FlowJoe uses it only when it is on the repository's own host; otherwise FlowJoe ignores it.
- **Guests.** Any guest can download a large file they can see, stop the download and start it again, just as you can; the download runs on your computer with your sign-in, and nothing in a folder hidden from the guest is ever downloaded for them. A guest's push sends its large files the same way.
- **Moving a large file.** Moved into another repository, or duplicated, a large file stays a large file. One you haven't downloaded keeps its **Download** button, which still works after the repository it came from is deleted (FlowJoe then fetches it from that repository's online copy); **Changes** reminds you to download it first, and once it's downloaded the new repository commits and sends it as a large file.
- **Not yet:** large files open from their slot, not as text in the editor, and Joe can't edit them.

### Use an SSH remote (macOS and Linux)

SSH remotes work on macOS and Linux. On Windows they are not supported yet; FlowJoe tells you so and asks you to use an `https://` address.

Before using SSH, add or unlock your key in the SSH agent available to FlowJoe. FlowJoe does not copy private keys into the Flow, repo history, or workspace. If the agent starts after FlowJoe, restart FlowJoe so it can see the agent connection.

FlowJoe uses the system OpenSSH client from a fixed location, not your `PATH`: `/usr/bin/ssh` or `/bin/ssh`. On Linux, install an OpenSSH client if neither path exists.

SSH hosts must already have a trusted key in your standard OpenSSH `known_hosts` file (`~/.ssh/known_hosts`). Verify the host key fingerprint against information from your Git host before adding it. FlowJoe checks the host key strictly and stops if the host is unknown or has changed; it does not ask to trust a new host inside the app.

<Warning>
Unknown or changed host keys are rejected. FlowJoe never offers a prompt that trusts a new host automatically.
</Warning>

The **Graph** section shows commit history, branch and tag labels, and commit details; when GitHub has commits your branch does not, they appear on a separate purple lane that curves back to your branch where the two meet. Use **Show Git Output** in the Graph options or repository menu to inspect recent Git activity.

## Preview repository files

In the Explorer menu, **Preview File** displays the repository file itself. **Preview Slot Item** opens the corresponding gallery preview for that exact file item, including the selected child of a stack. The repository preview can show text and code, Markdown, HTML, images, audio and video, PDFs, extracted Office text, and ZIP file listings. Office previews show extracted content rather than a full-fidelity editable Office document; a ZIP preview lists its entries rather than opening them as a folder.


<Warning>
HTML and Markdown previews show saved content without running scripts or contacting websites. Images and styles from the same repository can load within preview limits. A preview does not start your app or development server, and custom fonts may not appear.
</Warning>

## Set changes aside (Stash)

**Stash** puts your uncommitted work away and returns the gallery to the last commit, so you can switch tasks without committing half-finished work. Open the **Stash** menu in Source Control and choose **Stash…**. In the **Stash Changes** window you can add an optional message, see what will be stashed, and turn **Include new files** on or off (it is on by default). New files that sit inside a stack are left out and stay in the gallery. Files you had staged come back staged.

Your stashes appear in a **Stashes** group in the panel. Stashes stay on this computer: they are never pushed, and Sync, Pull, Push, and Fetch ignore them.

- **Pop** brings a stash back and removes it from the list. **Pop Latest Stash** takes the newest one, or choose **Pop Stash…** to pick.
- **Apply** brings a stash back and keeps it in the list.
- **View Stash…** shows the files in a stash.
- **Drop Stash…** deletes one stash, and **Drop All Stashes…** deletes every stash in the repository. Both ask you to confirm first.

If a file changed in the gallery since you stashed it, the **Restore** window asks which version to keep for each such file: **Keep Mine** or **Keep Stashed**, or **Compare…** to combine them by hand. Nothing changes until you confirm. If you kept your own version of a file, the stash stays in the list.

After you stash or pop, a toast offers **Undo** for 5 seconds. You can also press <kbd>Delete</kbd> on a focused stash row to drop it.

## Bring FlowJoe into your IDE

For another way to stay close to your project, the optional **FlowJoe extension for VS Code** puts the Flow in your editor’s sidebar. Edit names, slot and stack notes, Flow and node summaries, and node status while keeping your code editor open.

If you have the FlowJoe source checkout:

1. In your editor, run **Extensions: Install from VSIX…** and select the supplied `integrations/vscode-flowjoe/vscode-flowjoe-0.0.4.vsix` file.
2. Open FlowJoe’s desktop app and enable **Settings → Joe AI → Agent Bridge (MCP)**.
3. Choose **Connect to FlowJoe** in the editor’s FlowJoe panel. If prompted, use the bridge token shown in FlowJoe.
4. Use **Refresh Flow** to bring in changes made in FlowJoe.

Use version **0.0.4 or later**. Earlier installers do not include the connection protection added in this audit. The extension connects only to FlowJoe on your own computer and refuses redirects. Change its connection settings in your editor’s user or machine settings; a project’s workspace settings cannot override them.

Edits wait for approval in FlowJoe unless you enable **Apply changes without asking** (Agent Bridge → Advanced). This extension edits Flow content; repository working-file editing happens in the FlowJoe workbench. It uses refresh rather than a continuous stream of updates. Browser guests use the shared repository workbench in their browser.


## What Joe can read

With Joe's Read access in the desktop app, using an OpenAI or Gemini API model or a tool-capable CLI brain, you can ask about saved repository changes and commit identities, or ask for a saved-versus-committed file comparison. Joe can distinguish staged and unstaged files when the current Changes list is available. A read does not open or refresh that list. If its state cannot be verified, Joe reports staging as unavailable.

Ask explicitly for saved text, an open unsaved draft, or an already-open historical file. Joe labels the source and checks that the file and draft version have not changed while reading. If a draft is not open, Joe reports that it is unavailable. Private and Hidden-from-Joe contents remain excluded. Large results are read in bounded parts; unverified deleted paths and oversized files are unavailable. These reads do not edit, save, stage, commit or run commands. External agents connected through the Agent Bridge, including the [FlowJoe CLI](/cli/action-reference#read-repository-state--read_repository), can make the same reads with Read or Propose access. Guests can make these reads for files and repositories visible in their shared Flow when Joe is enabled. Scheduled tasks cannot.


An open historical tab can be read only while the file is still present and readable in that repository. Deleting the current file or making it private revokes the old tab's read access. FlowJoe checks again before each provider request, including after a wait for approval or a reference chapter; changed files or access cancel the response instead of sending stale text.

## Ask Joe to change a file

You can ask Joe to make one exact text change to one existing file in a repository, for example "in `src/main.js`, change `retries = 3` to `retries = 5`". Joe can base the change on the saved file or on your open unsaved draft, and he says which. This works in the desktop app for your own chats, and for an Edit guest's Joe: the change is saved on the owner's computer, the same way as the guest's own Save, and only for files the guest can see. An external agent with Propose access, including the FlowJoe CLI, can propose the same edit; it arrives on an **Agent request** card for you to review, unless that CLI command uses `--autoapprove` (see [the CLI guide](/cli/gallery-changes#change-text-in-one-repository-file--editrepofiletext)). It is not available to scheduled tasks, since no one reviews the change.

Joe's answer is a review card, not a change. The card names the file and branch, says what the change is based on, and states **Apply saves this file** and **No commit or push is included**. A read-only before-and-after comparison opens in the repository editor, labeled **Saved file · before** (or **Your unsaved draft · before**) and **Joe’s proposed edit · after**. Look at the exact lines, then choose **Apply**, **Revise** to ask Joe for something different, or **Reject**. Nothing is written until you apply.

If you type in that file after the preview, Apply turns off and the card says **The file changed after this preview. Ask Joe for a fresh proposal.** The old text must also appear exactly once in the file; if it is missing or appears more than once, Joe is told and can propose again. A file edit comes on its own card, never mixed with other changes.

Applying saves the file in FlowJoe, the same as pressing **Save**. It does not write to a folder on your computer and does not commit or push; use **Source Control** for that. If the save cannot be completed, the edit stays in memory with FlowJoe's recovery copy and the open tab shows Joe's text until storage is available again. Undo (the card's undo or "undo your last change") puts back the previous version and the text your editor showed before, unless you saved that file again or typed in its open tab since, in which case nothing is undone.


## Ask Joe to work with repositories

You can ask Joe to create a repository, clone a link, list your GitHub repositories, or clone several into separate nodes. For example: “List my GitHub repositories and clone the ones I choose under Projects.” Your signed-in account can access private repositories as well as public ones; Joe never asks for or receives your token.

Joe lists the repository name, whether it is private on GitHub, its default branch and its estimated size. Reading the list or repository status makes no change. Before downloading or changing anything, Joe shows an approval slot. Untick repositories you do not want; the count and size update. Nothing starts with none selected.

Clones run one at a time. Each successful repository appears as its own node, with a link you can select. A failed clone names the repository and leaves the others free to continue. Stop ends the current download and the remaining work; completed repositories remain. A failed save is reported rather than presented as saved.

You can also ask Joe to fetch, pull, sync, commit, push, create a branch, open a branch as another node, or merge branches. Joe can first prepare the current Changes list when needed; a commit proposal then shows its exact files and drafted message before you approve. Branches open as separate nodes so the current one is preserved. Merge questions use the same review windows as Source Control. An unfinished merge says **Needs your choice**; closing its question or conflict window does not commit it. Stop also prevents the next step of other Git actions while a confirmation or preparation is waiting; work already completed keeps its actual result. A push changes the remote repository and has no ordinary Flow undo.

### Guests and GitHub repositories

As the owner, you can list and clone every repository your signed-in GitHub account can access, including private ones.

Guests can list your account’s **public** repositories and any repository already visible in their shared Flow, even if it is private on GitHub. Your other private GitHub repositories stay unavailable to them. A View guest can read the permitted list and status; an Edit guest can ask Joe to create and clone nodes within their shared area. Your computer checks the guest’s current access again before creating each node. Private Flow folders and folders hidden from that guest stay hidden.

## Local folder import safety

When importing a repository folder, FlowJoe reads working files through the folder it opened.
Replacing a subfolder with a symbolic link cannot redirect those reads elsewhere. A symbolic-link
file is saved as its link text rather than loading its target. Files that change while being read
are skipped; ordinary hardlinked files remain supported.

Portable `.fj` and `.json` exports use the same per-Private-node password choice and warning as **Make This a Repository**. Every Private node starts excluded; included nodes carry history under the export’s ordinary history choices. See [Export & import](/portability/export-import#choose-private-nodes).
